# LLM 大规模重写工作流 (LLM-Driven Large-Scale Rewrite Workflow)

> **来源**: Jarred Sumner, [Rewriting Bun in Rust](https://bun.com/blog/bun-in-rust) (2026-07-08)
> **一句话**: 别指望 AI 一次写对，而是搭一条「让错藏不住」的流水线——用测试定对错、用对抗审查兜质量、用编译错误当工单、用人把方向。

## 1. 核心思想

大规模重写（数万至百万行）可以在极短时间内由 1 名工程师 + 多个 AI 并行完成，前提是把「让模型写代码」变成「构建可验证、可并行、可审查、可纠偏的工程流水线」：

- **测试当裁判**: 「写对了没」由语言无关的测试套件说了算，不靠感觉。
- **审查当双保险**: 写的人不审自己写的东西，安排独立「杠精」专挑毛病。
- **错误当工单**: 编译/测试报错 = 可并行分发的任务队列，AI 越多干得越快。
- **人当主编**: 人定义规则、盯流程、最后拍板，不亲自写每一行。

## 2. 适用条件（先自查，不满足别硬套）

| 前提 | 说明 |
|---|---|
| 有语言无关的测试套件 | 百万级断言最佳；没有足够测试，先补测试再谈重写 |
| 有深度上下文的人 | 至少一人完全理解原代码库，能判断「翻译得对不对」 |
| 代码可机械移植 | 选「翻译」而非「重写」，最小化行为变化，降低验收难度 |
| 模型 + 工具链到位 | 能稳定处理大 diff 的模型、可编排多 agent 的工具、足够的算力预算 |

## 3. 流程总览

1. **出考卷**：定对错——语言无关的测试套件当唯一验收标准
2. **定规范**：人机共建移植指南（PORTING.md）与生命周期表（LIFETIMES.tsv）
3. **试运行**：先拿 3 个文件验证流程，再全量铺开
4. **全量执行**：1 写 + 2 对抗审查 + 1 应用的闭环，多 agent 并行
5. **错误当工单**：编译/测试报错按模块分组，分发给并行 agent 修复
6. **验证**：本地全绿 → CI 全平台全绿 → 人工确认测试真跑 → 合并

## 4. 执行步骤

### Phase 0: 先降风险

1. 确认「一次性全量移植」优于「增量重写」：增量会积累等待删除的临时代码，短期中期都痛苦。
2. 用小范围试运行验证流程（Bun 先试 3 个 .zig 文件，再铺开 1,448 个）。

### Phase 1: 定义验收标准（出考卷）

1. 确认/建立**语言无关的测试套件**（不依赖实现语言的断言体系）。
2. 明确目标是**机械移植**：结构与原代码尽量一一对应，行为变化最小。
3. 提前定好「防假绿」手段：测试必须真跑、不许跳过、不许 stub 糊弄。

### Phase 2: 人机共建规范

1. 与 AI 讨论模式映射（语言 A → 语言 B 的类型/惯用法），产出**移植指南**（如 PORTING.md）。
2. 让 AI 分析每个结构体字段的生命周期，产出**生命周期表**（如 LIFETIMES.tsv），供所有执行者查询。
3. 对这两份规范本身再做一轮对抗审查，消除冲突建议，**人工通读确认**。

### Phase 3: 全量执行（写-审-修闭环）

每个任务固定编组：**1 个 implementer + 2 个 adversarial reviewer + 1 个 fixer**。

- **implementer**: 只写代码，不审。
- **adversarial reviewer**: 独立上下文窗口，只看 diff，被明确要求「假设代码是错的」，穷举出错理由。
  - 既审「语义与原代码是否一致」，也审「是否遵守 PORTING.md / LIFETIMES.tsv」。
- **fixer**: 应用审查结论，落地改动。

### Phase 4: 错误当工单（并行提速）

1. 先拆模块/crate，解决循环依赖，为并行铺路。
2. 跑编译器/测试，把报错**按模块分组存成文件** = 任务队列。
3. 多个 agent 并行领工单：每个模块 1 修 2 审 1 应用。
4. **隔离防踩踏**: 各 agent 独立 worktree；禁止 git stash / git reset 等危险命令；只在开头跑一次编译，结束时才统一提交。

### Phase 5: 验证与合并

1. 本地跑通冒烟（bun --version → 单文件测试 → 全部测试）。
2. CI 全平台全绿（Bun 为 6 平台 420 次构建）。
3. **人工确认测试真的在跑、没被跳过**，本地实测后再按 merge。

## 5. 关键规则（反模式清单）

| 规则 | 原因 |
|---|---|
| 不许用 stub/空壳函数糊弄编译 | AI 会「先编过再说」，把问题藏起来 |
| 「需要一段话解释 workaround 没问题」= 代码是错的，回去重写 | 堵死 AI 的狡辩与投机 |
| 写的人不审，审的人不写 | 消除「作者想让代码通过」的自利偏误 |
| 审查者默认代码是错的 | 反向思维才能抓到「编译通过但语义错误」 |
| 出问题修「生成代码的流程」，不手修单个代码 | 让同类错误不再复发 |
| 大改动前先试运行 | 避免流程性错误被放大 1,000 倍 |

## 6. 成本参考（Bun 实例）

- 规模: 535K 行 Zig → 约 780K 行 Rust，落地 diff +1,009,272 行。
- 时间: 11 天（6,502 commits），峰值 64 个 agent 并行、1,300 行/分钟。
- 算力: 59 亿 uncached input + 6.9 亿 output + 720 亿 cached input tokens，约 16.5 万美元 API 成本。
- 人力等价: 约 3 名全上下文工程师全职 1 年。
